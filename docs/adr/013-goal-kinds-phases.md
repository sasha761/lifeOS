# ADR-013 — Цели без измерений, статус цели и дата начала

- **Статус:** Accepted
- **Дата:** 2026-11-23
- **Связанные задачи:** LFS-225; решения владельца в [LFS-225](../tasks/LFS-225.md) и [LFS-223](../tasks/LFS-223.md)
  (пункты 10–11); дополняет [ADR-007](007-goals.md), [ADR-008](008-transactional-audit.md),
  [ADR-010](010-goals-api-progress.md); доска — LFS-229

## Контекст

ADR-007 описывает одну модель цели: единица, старт, цель и направление обязательны. У многих целей естественного
числа нет: «найти работу», «пройти курс», «запустить проект». Мастер (LFS-219) заставлял придумать «20 откликов»
или «8 этапов», а это противоречит правилу «никаких выдуманных метрик».

Решения владельца:

- цель без измерений имеет статус «В процессе → Достигнута», достигнутой её отмечает сам человек;
- нужна дата начала вместе со сроком;
- у любой цели четыре статуса: «Запланирована», «В процессе», «На паузе», «Достигнута»; на доске они станут
  колонками (LFS-229);
- в «Запланирована» цель попадает только вручную; исключение — новая цель с датой начала в будущем.

Архив по-прежнему терминален (ADR-007). Удаление — LFS-216.

## Решение

### Вид цели

Поле `kind`: `numeric` (как раньше) или `unmeasured`. Вид задаётся при создании и не меняется.

- **`numeric`.** Единица, старт, цель и направление обязательны, правила ADR-007 и дополнения LFS-217 прежние.
- **`unmeasured`.** Поля `unit`, `unit_label`, `baseline`, `target`, `direction` равны `null` в БД и в DTO.
  - Создание без `kind` даёт числовую цель, как до LFS-225.
  - Цель без измерений не принимает ни одного из пяти полей определения: строгая схема даёт 400.
  - Правка определения у такой цели — 409, как правка определения цели с измерениями.

**Где держится правило:**

- **Контракт** — объединение двух строгих схем по `kind`.
- **Домен** — проверка в `update`.
- **SQL** — `goals_kind_definition_check`: у `numeric` четыре значения не `NULL`, у `unmeasured` все пять `NULL`.
  Остальные CHECK значений и направления на `NULL` проходят, поэтому именно эта проверка решает, у какого вида
  определение пустое.

**Измерений у цели без измерений нет:**

- **API** отвечает `409 CONFLICT` — так же, как на измерение архивной цели. Конфликт выбран вместо 400, потому что
  тело запроса корректно, а мешает состояние цели.
- **SQL** не даёт вставить строку: внешний ключ измерения `(user_id, goal_id, unit)` ссылается на единицу цели, у
  цели без измерений её нет, и совпадения не будет. Отдельный CHECK для этого не нужен.

### Статус (`phase`)

`status` остаётся `active | archived`. Статус активной цели — новое поле `phase`: `planned`, `in_progress`, `paused`
или `achieved`. Время последней смены хранится в `phase_changed_at`. Отдельное поле, а не новые значения `status`,
выбрано по двум причинам:

- фильтры, счётчики, вкладки «Активные / В архиве» и SQL-защита архива (`status = 'active'`) остаются прежними;
- у архивной цели сохраняется последний статус.

- **Новая цель.** Если `starts_at` позже момента вставки (время БД, как у `created_at`), статус `planned`, иначе
  `in_progress`. Дальше статус меняет только человек. Автоматического перехода по дате нет, отметки «Достигнута» по
  100% тоже: процент числовой цели от статуса не зависит.
- **Переход.** Возможен между любыми двумя из четырёх статусов, у целей обоих видов. Это отдельная команда
  `PATCH /api/v1/goals/:id` с телом только `{ "phase": … }`: смешивание с правкой или архивом — 400.
  - Нужен `Idempotency-Key`, в квитанциях новая операция `phase`.
  - Тот же статус ещё раз — успех без изменений и без события, как повторный архив.
  - Архивная цель — 409.
  - Чужая, несуществующая или битая — 404.
- **Измерения.** Числовой цели их можно добавлять в любом статусе, кроме архива.
- **Пример.** Пример LFS-218 при смене статуса остаётся примером: статус не считается правкой цели.

### Дата начала

`starts_at` — необязательный абсолютный момент для цели любого вида, по образцу срока (ADR-007, ADR-010):

- ISO с явным offset, до миллисекунд, хранится в UTC;
- в интерфейсе дата начала — начало выбранного дня в поясе пользователя (`startOfLocalDay`), срок — его конец.
  Если полночь в этот день пропускается переводом часов, берётся первый существующий час.

Если заданы обе даты, начало не позже срока. Это проверяют контракт, домен и `goals_starts_at_check`. Домен
сравнивает изменённую дату с сохранённой второй — так правка одной даты не обходит правило. Начало правится у
любой цели, в том числе после измерений: на прогресс оно не влияет.

### Прогресс

У цели без измерений в `GoalDetails.progress`:

- `status: "unmeasured"`;
- `progressPercent`, `methodology`, `unit`, `baseline`, `target`, `current`, `provenance` — `null`;
- `measurementCount` — 0;
- `explanation` — слово статуса («Запланирована», «В процессе», «На паузе», «Достигнута»), а не
  «Недостаточно данных».

Общего процента по сфере нет. Dashboard и страница сферы показывают у такой цели её статус.

### Журнал и повторы

- **Смена статуса** пишет `goal.updated` с `changed_fields: ["phase"]`. Других полей в таком событии нет, оба
  статуса лежат в снимках.
- **Снимок цели** дополнен полями `kind`, `phase`, `starts_at`. В событиях до LFS-225 их нет, и схема это
  допускает. Поля определения в снимке могут быть `null`.
- **Правка начала** — `changed_fields` содержит `starts_at`, значения до и после берутся из снимков.
- **Журнал** показывает «Статус изменён: В процессе → Достигнута» и «Дата начала изменена: …».
- **Отпечаток создания.** Значения по умолчанию, которые добавил LFS-225 (`kind: numeric`, `starts_at: null`), в
  отпечаток запроса не входят. Повтор запроса создания, отправленного до обновления, совпадает со своей квитанцией,
  а не становится конфликтом. Отпечатки остальных команд не меняются.

## Миграция и откат

`0010_goal_phases.sql` создана `pnpm db:generate --name goal_phases`.

**Изменения в `goals`:**

- снимает `NOT NULL` с `unit`, `baseline`, `target`, `direction`;
- добавляет `kind` (по умолчанию `numeric`), `phase` (по умолчанию `in_progress`), `phase_changed_at`, `starts_at`;
- добавляет CHECK `goals_kind_check`, `goals_kind_definition_check`, `goals_phase_check`, `goals_starts_at_check`.

**Изменения в других таблицах:**

- CHECK допустимых ключей снимков в `activity_events` пересоздаются с новыми полями;
- CHECK операций квитанций в `goal_command_receipts` пересоздаются с операцией `phase`.

Последняя строка миграции дописана руками после генерации: `phase_changed_at = created_at` у существующих целей.
Они в работе с момента создания. События, квитанции и значения целей не переписываются.

**Откат кода к LFS-224 после миграции несовместим с данными:**

- старый контракт не разбирает цель с `kind = unmeasured`, цель с `NULL` в определении, события со снимками `kind`,
  `phase`, `starts_at` и `changed_fields` `phase`/`starts_at`;
- журнал, список целей и Dashboard такого аккаунта перестанут читаться.

Перед откатом цели без измерений удаляют. Откат схемы — отдельная forward-миграция, применённые файлы не меняются.

## Альтернативы

- **Новые значения `status`** (`planned | in_progress | paused | achieved | archived`). Ломают фильтры, счётчики,
  курсоры, SQL-защиту архива и тексты «Активные». Последний статус архивной цели теряется. Отклонено.
- **Отметка «достигнута» только у целей без измерений.** Тогда перетаскивание числовой цели на доске ничего не
  значит. Отклонено решением владельца (LFS-223).
- **Автоматическая отметка «Достигнута» по 100%** и автоматическое «Запланирована → В процессе» в дату начала.
  Система меняла бы смысл без действия человека. Отклонено решением владельца.
- **400 на измерение цели без измерений.** Тело запроса корректно, мешает состояние цели — как у архива, поэтому
  409.
- **Отдельная таблица или JSON для цели без измерений.** Дублирует владельца, аудит, удаление и чтение. Отклонено.

## Последствия

- Чек-листов и этапов нет (модуль Проекты, этап 9). Перевода числовой цели в цель без измерений и обратно тоже нет.
- Создание цели без измерений в интерфейсе — LFS-227 (мастер) и LFS-228 («Новая цель»). Пока только через API.
- Колонки доски и перетаскивание — LFS-229. Пункты меню «⋯» уже дают любой переход, это замена перетаскиванию
  (WCAG 2.5.7).
