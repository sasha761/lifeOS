# LFS-218 — Пример по выбору пользователя

**Этап:** 2 — LifeOS Core (вставка в очередь после LFS-217, перед LFS-219, по запросу владельца 2026-11-18;
переписана 2026-11-18: пример больше не создаётся автоматически)
**Зависимости:** LFS-216 (удаление целей), LFS-217 (правка до первого измерения), LFS-204 (Dashboard), LFS-210 (аудит);
[ADR-007](../adr/007-goals.md), [ADR-009](../adr/009-goal-measurements.md); [ONBOARDING](../reference/ui/ONBOARDING.md)
**Макеты:** `28-onb-example.png` (Кабинет с примером); карточка «Посмотреть на примере» на `23-onb-start.png`
и `31-onb-reopen.png` подключается в LFS-220. Точные размеры — `docs/reference/ui/html/`.
**Цель:** пользователь сам решает, загрузить ли пример: 7 целей во всех шести сферах с примерными измерениями.
Пример помечен, становится «своим» после правки и удаляется одной кнопкой.

## Почему

Первая версия задачи создавала набор автоматически при регистрации и один раз во всех существующих аккаунтах.
Владелец решил иначе: пустой аккаунт видит выбор (LFS-220), а пример появляется только по явному действию
пользователя. Эта задача делает сам пример, метки и удаление. Кнопки выбора — LFS-220, вопросы по сферам — LFS-219.

## Решения владельца · 2026-11-18
1. **Набор** (сроков нет ни у одной цели):

   | Сфера | Цель | Единица | Старт → Цель | Пример измерения |
   |---|---|---|---|---|
   | Finance | Накопить 5 000 $ | USD | 0 → 5 000 | 1 200 |
   | Languages | Английский до уровня B2 | своя: «уровень (A1=1 … C2=6)» | 2 → 4 | 3 |
   | Health | Ходить в зал 3 раза в неделю | своя: «тренировок в неделю» | 0 → 3 | 2 |
   | Health | Бокс раз в неделю | своя: «тренировок в неделю» | 0 → 1 | 1 |
   | Skills | Рейтинг Lichess 1500 | своя: «рейтинг Lichess» | 1000 → 1500 | 1150 |
   | Work | Прочитать 6 книг по профессии | шт. | 0 → 6 | 2 |
   | Projects | Запустить личный проект | своя: «этапов» | 0 → 5 | 1 |

   Для зала и бокса измерение — сколько раз было за последнюю неделю; текущее значение — последнее измерение
   (ADR-009), как у всех целей.
2. **Примерные измерения есть.** Это сознательное исключение владельца из правила AGENTS.md «никаких фиктивных
   метрик»: примеры явно помечены и никогда не выдаются за данные пользователя.
3. **Автоматически набор не создаётся никому:** ни при регистрации, ни в существующих аккаунтах, включая аккаунт
   владельца. Только по действию пользователя: попап первого входа или Настройки → «Начальная настройка» (LFS-220).
4. Пример удаляется целиком кнопкой «Удалить все примеры». Загрузить его снова можно, когда в аккаунте не осталось
   примерных целей.
5. Примерная цель становится своей при первой правке или первом собственном измерении: метка «Пример» снимается,
   и «Удалить все примеры» её больше не трогает.

## Область изменений
- `packages/contracts` — единица `USD`; источник измерения `example`; источник события `starter`; поле цели
  `origin` (`manual` | `starter` | `onboarding`; значение `onboarding` используется с LFS-219) в DTO цели и Dashboard;
  DTO запросов и ответов примера
- `packages/db` — миграция: CHECK единиц целей и измерений (USD), CHECK источников измерений и событий, колонка
  `goals.origin` (`NOT NULL DEFAULT 'manual'` + CHECK); unit of work применения и удаления примера
- `packages/domain` — описание набора (версия 1), команды `applyStarterPack(actor)` и `removeStarterPack(actor)`;
  все цели и измерения создаются теми же доменными правилами и с аудитом, что ручные
- `apps/web/server/*`, `app/api/v1/starter-pack/route.ts` — `POST` и `DELETE`
- `apps/web/components/goals/*`, `components/dashboard/*`, `lib/goal-presentation.ts` — USD, чип «Пример», баннер
- ADR-007 и ADR-009 (USD, `origin`, примерные измерения), `docs/api/contracts.md`, `README.md`

## Задание
- [ ] `POST /api/v1/starter-pack`: одной транзакцией 7 целей с `origin = starter`, 7 измерений с `source = example`
  и заметкой «Пример — замените своим значением или удалите», события аудита с источником `starter`.
  Если в аккаунте уже есть цель с `origin = starter` — 409 `CONFLICT` «Пример уже в аккаунте», ничего не создаётся.
  Двойной клик и параллельный запуск не дают двух наборов: блокировка на пользователя в той же транзакции плюс
  `Idempotency-Key`, как у остальных записей.
- [ ] `DELETE /api/v1/starter-pack`: одной транзакцией удаляет все цели с `origin = starter` вместе с измерениями,
  событиями и квитанциями (тот же механизм, что в LFS-216). Ответ — число удалённых целей. Цели `manual` и
  `onboarding` не трогаются. Повтор после обрыва связи не показывает пользователю ошибку.
- [ ] Примерная цель становится своей: любая успешная правка цели или первое собственное измерение меняют `origin`
  на `manual` в той же транзакции; `goal.updated` фиксирует `origin` в `changed_fields`. При смене определения
  (LFS-217) и при первом собственном измерении примерные измерения этой цели удаляются в той же транзакции с аудитом.
- [ ] Ничего не создаётся автоматически: нет хука регистрации, нет команды массового применения к аккаунтам,
  нет флага `STARTER_PACK_ENABLED`. Прежние тестовые фикстуры с пустыми сферами не меняются.
- [ ] UI:
  - чип «Пример» у цели с `origin = starter` (список целей, панель цели, строки Dashboard, страница сферы) и у
    измерения с `source = example`;
  - в панели цели с одними примерными измерениями — подсказка «Это пример: поправьте старт и цель под себя или
    удалите цель»;
  - баннер на `/dashboard`, пока есть примерные цели, по `28-onb-example.png`: «Это пример», текст и кнопка
    «Удалить все примеры» (опасный тон) с подтверждением «Удалить все примеры? Удалим N примерных целей вместе
    с их измерениями и историей. Цели, которые вы поправили или где есть ваши измерения, останутся.»
    → «Удалить N целей» / «Отмена». Фокус возвращается на кнопку, после удаления — сообщение и обновлённый Dashboard;
  - кнопку «Пройти настройку вместо примера» в баннере добавляет LFS-220. Кнопки «Заполнить примером» в UI в этой
    задаче нет: она появится в попапе LFS-220, а тесты применяют пример через API.
- [ ] Dashboard DTO: число примерных целей для баннера, без запроса на каждую цель.
- [ ] Единица `USD`: в выборе единицы, форматирование «5 000 $» по UI_GUIDELINES, точность 2 знака в контракте и CHECK.

## Acceptance criteria
- [ ] Контракт: каждое определение набора проходит контракт создания цели.
- [ ] PostgreSQL integration: применение создаёт ровно набор; повтор, двойной и параллельный запуск не дублируют;
  409 при наличии примеров; удаление стирает только `starter`; после удаления пример применяется снова; второй
  пользователь изолирован; откат не оставляет части набора; правка и собственное измерение снимают `starter`;
  миграция на чистой и текущей схеме, существующие цели получают `origin = manual`.
- [ ] Регресс: регистрация нового пользователя не создаёт ни одной цели.
- [ ] HTTP-тесты: 401, Origin, тело запроса у `DELETE`.
- [ ] e2e на 1280 и 390 (пример применён через API): чипы и баннер, правка старта стартовой цели снимает чип,
  «Удалить все примеры» с подтверждением оставляет поправленную цель.
- [ ] `pnpm verify`, `pnpm test:ui`, `pnpm ui:shots` зелёные; таблица отличий от `28-onb-example.png` по UI_GUIDELINES.

## Ручные действия
Миграция рабочей базы (`pnpm db:migrate`) — только с отдельного разрешения владельца. Применять пример к
существующим аккаунтам не нужно и нельзя.

## Вне scope
Попап первого входа и кнопка в Настройках (LFS-220), вопросы по сферам (LFS-219), английские названия набора,
валюты кроме NOK и USD, обмен валют, цели «за период» как отдельный режим.
