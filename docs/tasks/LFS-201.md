# LFS-201 — Better Auth: регистрация, вход, восстановление доступа

**Этап:** 2 — LifeOS Core  
**Зависимости:** Stage 1 завершён; LFS-101–109  
**Цель:** Безопасная учётная запись для личного MVP без открытой публичной регистрации.

## Область изменений
- `apps/web` — auth route, login/signup/reset UI, guards
- `packages/db` — Better Auth schema, migrations
- `packages/contracts`/`packages/config` — auth/env schemas
- документация и тесты

## Задание Codex
- [ ] Осмотри реальные пакеты Stage 1; установи Better Auth и Drizzle adapter в зафиксированных совместимых версиях, без установки «latest» вслепую.
- [ ] Создай корректную миграцию таблиц Better Auth (`user`, `session`, `account`, `verification`), не меняя их имена/типы произвольно; доп. поля пользователя вводятся отдельно в LFS-202.
- [ ] Реализуй email/password signup, login, logout, server-side session retrieval и защищённые маршруты. Закрой новые регистрации email allowlist из env (case-insensitive trim), сохрани контроль сервером; логин существующего пользователя не блокируется allowlist.
- [ ] Подготовь восстановление доступа через подписанный/одноразовый токен и корректный email sender: в dev — явный тестовый транспорт, в prod — конфигурируемый реальный провайдер. Не выдавай «письмо отправлено», если отправка невозможна; не логируй reset-token.
- [ ] Создай `/auth/sign-in`, `/auth/sign-up`, `/auth/forgot-password`, `/auth/reset-password` с валидацией/ошибками, доступные с клавиатуры; маршруты `/dashboard` и `/goals` требуют сессии.
- [ ] Защити серверные API, но не полагайся лишь на middleware или скрытие кнопок; не делай реальную авторизацию через Telegram в этой задаче.

## Acceptance criteria
- [ ] Интеграционные тесты Better Auth + DB; reject signup вне allowlist; session expiry/logout; reset token reuse.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` либо реально доступные эквиваленты.
- [ ] Проверить dev signup/login/logout/reset вручную; `git diff --check`.

## Проверки / тесты
- [ ] Незарегистрированный email не может зарегистрироваться, allowlisted email может; проверка на backend.
- [ ] Существующий пользователь входит/выходит, обновление страницы не теряет сессию.
- [ ] Неавторизованный API получает 401, защищённый UI направляет на вход; logout инвалидирует сессию.
- [ ] Dev reset flow проверен, prod sender не замаскирован заглушкой.
- [ ] В базе нет plain-text паролей или reset-токенов.

## Вне scope
Telegram linking, OAuth, org/workspaces, подписки и роли, кроме обычного пользователя.

## Дополнительные решения
Allowlist — мера ограничения пилота, а не полноценная стратегия безопасности. Используй конфигурацию Better Auth согласно версии, закреплённой в ADR.

## Результат LFS-201 · 2026-11-14

Реализованы Better Auth 1.7.18 (email/password) с закрытой регистрацией,
вход/выход, восстановление доступа по одноразовому токену и защищённые
`/dashboard`, `/goals`, `/api/v1/me`. Решения и ограничения —
[ADR-005](../adr/005-auth.md); версии и аудит зависимостей — [ADR-001](../adr/001-stack.md).

- **Схема:** миграция `packages/db/drizzle/0001_better_auth.sql` (`user`, `session`, `account`, `verification`),
  без изменения имён/типов генератора Better Auth; migrator вынесен в `@lifeos/db/migrations`.
- **Allowlist:** `AUTH_SIGNUP_ALLOWLIST` → `createSignupPolicy` (`@lifeos/domain`) → Better Auth `user.validateUserInfo`;
  вход существующих пользователей не ограничен.
- **Сброс пароля:** токен хранится SHA-256 хэшем, одноразовый, 60 минут, после сброса все сессии отзываются;
  доставка — `outbox` (dev/test, запрещён в production) или SMTP (nodemailer). Сбой доставки — 503
  `EMAIL_DELIVERY_FAILED`, а не «письмо отправлено» (Better Auth 1.7.18 сам ошибку глотает).
- **Охрана:** `requirePageUser()` на страницах, `requireApiUser()` в API, оптимистичный `proxy.ts` (307 гостю).
