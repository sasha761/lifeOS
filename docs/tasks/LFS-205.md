# LFS-205 — Доменная схема целей (`goals`)

**Этап:** 2 — LifeOS Core  
**Зависимости:** LFS-202, LFS-203  
**Цель:** Создать универсальную модель измеримой цели, которая одинаково пригодна для финансов, языков и будущих модулей.

## Область изменений
- `packages/db` — таблица goals и миграция
- `packages/domain/core/goals` — типы, правила, repository interfaces
- `packages/contracts` — Zod DTO
- integration/unit tests

## Задание Codex
- [x] Утверди и задокументируй поля: `id`, `user_id`, `domain_key`, `title`, `description?`, `unit`, `baseline`, `target`, `direction` (`increase|decrease`), `calculation_mode` (`manual|computed`), `metric_key?`, `status`, `due_at?`, timestamps.
- [x] На Stage 2 разреши создавать только `manual`-цели; `computed` зарезервирован и должен явно отклоняться до появления metric provider. Не создавай фиктивный computed provider.
- [x] Для значений применяй точный decimal/numeric подход вместо небезопасного JS float для валют; продумай единицы `NOK`, `count`, `minutes`, `percent`, `custom` и отсутствие конвертации единиц в Stage 2.
- [x] Сохраняй возможность направления `increase` (сбережения), `decrease` (долг); запрети target/baseline с бессмысленными значениями и обработай baseline==target через явное правило.
- [x] Спроектируй сервис создания/редактирования/архивирования goals с проверкой ownership, без веб-контекста. Документируй семантику статусов и времени.
- [x] Создай миграции и индексы `user_id`, `domain_key`, статус/даты; добавь тесты в настоящем PostgreSQL.

## Acceptance criteria
- [x] Migration apply на чистой БД и upgrade существующей Stage 1 базы.
- [x] Unit/domain tests; integration ownership, precision, validations.
- [x] lint/typecheck/test/build и `git diff --check`.

## Проверки / тесты
- [x] У каждой цели есть владелец и допустимый domain_key; schema без неконтролируемых JSON-модулей.
- [x] Смена направления и baseline не приводит к скрытому изменению истории.
- [x] База применяет ограничения, а контракт отклоняет неверные данные.
- [x] Computed goal не создаётся в Stage 2.

## Вне scope
UI, измерения, расчёт Dashboard, Telegram, банковские модели.

## Дополнительные решения
Оговорка: цели с `baseline === target` допускаются только по определённой бизнес-политике (например, already-reached при наличии подтверждённого current), а не через деление на ноль.

## Результат LFS-205 · 2026-11-15

Выполнена одна задача LFS-205 в ветке `lfs-205-goals`, на существующей
реализации LFS-202/203. Политики полей, единиц, статусов, времени, изменения
определения и отката — [ADR-007](../adr/007-goals.md). Master Plan не изменялся.

### Реализовано

- Contracts: `CreateGoalInput` / `UpdateGoalInput` / `Goal`, strict Zod schemas;
  decimal strings (22 целых, 8 дробных), сравнение через масштабированный BigInt.
  `NOK` ≤ 2 дробных знаков, `count` целое, `percent` 0..100, `minutes/custom`
  ≤ 8; `custom` требует `unit_label`. Нет float-кастов и конвертации единиц.
- Increase/decrease требуют target > / < baseline; равенство отклоняется
  явно, без искусственного already-reached и деления на ноль. Computed и
  ненулевой metric_key отклоняются и в contract, и SQL.
- `GoalsService` в domain: create/get/update/archive, branded Actor, safe
  errors. Правятся title/description/due_at; baseline/target/direction/unit/
  sphere/calculation mode неизменны. Архив терминален, сохраняет строки,
  повтор не меняет updated_at; правка архива — CONFLICT. SQL UPDATE metadata
  условен по active, поэтому гонка с архивом не восстанавливает цель.
- SQL repository: все обращения фильтруются `ownedBy(user_id, actor)`;
  чужой, отсутствующий и malformed id — одинаковый NOT_FOUND. Адаптер можно
  передать в Drizzle transaction; rollback проверен. Нет публичных HTTP writes
  до добавления audit в LFS-210 и API в LFS-207.
- `goals`: UUID, FK на user, обычные типизированные поля; точный numeric без
  typmod с CHECK границ/значащей дробной точности (без неявного округления),
  enum-подобные CHECK по ключам/единицам/статусам, finite timestamptz(3), два
  индекса с ведущим user_id. Даты DTO — ISO UTC, due_at принимает явный offset.

### Миграция

Новая `packages/db/drizzle/0003_goals.sql` сгенерирована Drizzle Kit, journal
дополнен четвёртой записью, создан `meta/0003_snapshot.json`. Только новая
таблица/constraints/indexes, DML над существующими таблицами нет. FK в новом
SQL неквалифицирован, как в `0001`, для изолированных schemas в тестах.
Старые 0000–0002 SQL не изменены (SHA-256 проверен после применения).

Миграция применена **и к test DB, и к локальной main DB**: main journal 3 → 4,
`goals` создана пустой; количество строк user/session/account/verification/
foundation fixture и число таблиц pg-boss сохранились. Существующие данные
не очищались. Откат кода не требует удаления схемы; схема откатывается только
отдельной forward-миграцией после сохранения данных (ADR-007).
