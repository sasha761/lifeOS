# LFS-215 — HTTP-статус 404 и redirect на страницах под потоковой оболочкой

**Этап:** 2 — LifeOS Core (доработка по рискам LFS-213, не блокирует Stage 3)
**Зависимости:** LFS-213; [ADR-004](../adr/004-next-routing.md); Next.js 16 docs
`apps/web/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/loading.md`, раздел «Status codes»
**Цель:** несуществующая страница отвечает 404, протухшая сессия — 307 на вход, а не 200 со страницей ошибки внутри.

## Почему

`apps/web/app/(web)/loading.tsx` оборачивает все страницы оболочки в Suspense. Ответ начинает отправляться со
статусом 200 до того, как страница выполнилась, поэтому `notFound()` и `redirect()` внутри страницы уже не могут
изменить статус: Next дорисовывает not-found в поток или делает redirect на клиенте. Пользователь видит правильную
страницу, но статус неверный:

| Адрес | Сейчас | Нужно |
|---|---|---|
| `/goals/не-uuid` | 200 + «не найдено» | 404 |
| `/goals/<uuid, которого нет или он чужой>` | 200, панель после запроса из браузера пишет «Запись не найдена или недоступна.» | 404 |
| любая защищённая страница с cookie от удалённой сессии | 200 + переход на вход на клиенте (проверить) | 307 на `/auth/sign-in?next=` |
| `/domains/<неизвестный ключ>` | 404 (LFS-213, rewrite в `proxy.ts`) | без изменений |

Для приватного приложения ущерб небольшой: мониторинг и smoke видят 200 там, где страницы нет, а redirect
зависит от JavaScript.

## Область изменений
- `apps/web/app/(web)/loading.tsx` и места скелетонов загрузки
- `apps/web/app/(web)/goals/(browse)/**` — проверка цели на сервере до начала потока
- `apps/web/server/*` — owner-scoped проверка существования цели (через существующий reader, без SQL в обход репозиториев)
- `scripts/build-smoke.ts` (статусы без БД) и `apps/web/tests/e2e/*` (статусы, которым нужна БД)
- `apps/web/README.md`, ADR-004 — если меняется правило размещения `loading.tsx`

## Задание
- [ ] Выбрать в плане и согласовать с владельцем способ. Варианты:
  1. опустить `loading.tsx` из корня `(web)` в сегменты, где нет `notFound()`/`redirect()` до данных, а проверки
     сессии и цели выполнить в layout над границей загрузки;
  2. оставить скелетон, но выполнять проверки до Suspense (сервером в layout сегмента);
  3. проверять в `proxy.ts` только формат id, а существование — вариантом 1 или 2.
- [ ] `/goals/[id]`: невалидный и несуществующий для владельца id → 404 на уровне HTTP; чужой id неотличим от
  несуществующего.
- [ ] Протухшая сессия на защищённой странице → 307 на вход с `next`.
- [ ] Скелетон загрузки остаётся там, где страница действительно ждёт данных (Dashboard, список целей).

## Acceptance criteria
- [ ] Статусы проверены автоматически: `/goals/не-uuid` → 404 и протухшая сессия → 307 — в build smoke или e2e;
  `/goals/<случайный uuid>` с живой сессией → 404 — в e2e (нужна БД). Прежние проверки smoke (включая неизвестную
  сферу → 404) не ослаблены.
- [ ] e2e без изменений поведения: выбор цели в списке не перезагружает список и не теряет фокус.
- [ ] `pnpm verify`, `pnpm test:ui` зелёные.

## Вне scope
Новые страницы ошибок и их дизайн, статусы API (там уже 404/401), страницы `(public)` и `auth`.
