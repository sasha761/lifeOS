# LFS-106 — Общие API-контракты, Zod и env validation

**Зависимости:** LFS-103, LFS-104, LFS-105  
**Цель:** единые типы, предсказуемые ошибки и защита границ ввода во всех будущих модулях LifeOS.

## Задание Codex

1. Создай `packages/contracts` с Zod-схемами для API-envelope `data`, `meta`, `errors` и типами через `z.infer`. Допустимые ошибки: `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `RATE_LIMITED`, `CONFLICT`, `INTERNAL_ERROR`, `AI_UNAVAILABLE`, `BUDGET_EXCEEDED`. Выбери **одну** непротиворечивую форму payload и опиши примеры.
2. Создай шаблон `ApiError`/error mapper и тонкий route-handler helper в `apps/web` для JSON 200/400/404/500 без утечки stack trace.
3. Добавь `request_id` / `correlation_id` на HTTP-границе, передавай их в безопасное структурированное логирование и будущую постановку jobs. Не генерируй ID в нескольких слоях без необходимости.
4. Создай `packages/config` для валидации `env` через Zod. Выдели конфиги `web`, `worker`, `database`; валидировать необходимые параметры **при запуске процесса**, а не при сборке/импорте клиентских компонент. Секреты не доступны в browser bundles.
5. Добавь в `GET /api/health` безопасный типизированный ответ по общему контракту. Для демо ошибок создавай **тестируемый helper**, не публичный «throw error» endpoint.
6. Подготовь unit tests на успешную/ошибочную валидацию env, неверный DTO, маппинг ошибок и наличие request ID.

## Acceptance criteria

- [ ] Web, worker и пакеты используют общий контракт; JSON ошибки единообразны.
- [ ] Некорректные переменные env вызывают явную диагностическую ошибку до нормальной работы процесса.
- [ ] Секреты не печатаются в логах и не попадают в клиентский bundle.
- [ ] HTTP errors не раскрывают stack traces и внутренние таблицы.
- [ ] Нет бизнес-эндпоинтов, авторизации или AI-tool реализаций.

## Проверки

Unit tests пакета contracts/config; `pnpm lint`, `pnpm typecheck`, `pnpm build`, ручная проверка health и malformed test payload в изолированном тесте.

## Вне scope

Не делать полноценный OpenAPI generator, Better Auth и CRUD; `Idempotency-Key` оформляется в контракте, реальные операции — позже.
