# LFS-108 — CI, автоматические проверки и воспроизводимые сборки

**Зависимости:** LFS-107  
**Цель:** каждый pull request автоматически проверяет качество кода и совместимость Web/worker/PostgreSQL.

## Задание Codex

1. Настрой workflow GitHub Actions **если репозиторий размещён на GitHub**; если нет — создай рабочий YAML для будущего подключения и проверь локально всё, что доступно. Права GitHub доступ не предполагай.
2. CI должен использовать версию Node/pnpm из `LFS-102`, устанавливать зависимости через frozen lockfile и запускать (в зависимости от фактических scripts): `lint`, `typecheck`, `unit tests`, **integration tests с настоящим PostgreSQL**, `build` для Web и worker.
3. Включи PostgreSQL service container с отдельной тестовой БД и запуск миграций без персональных секретов. Не используй продакшн `DATABASE_URL`; не разрешай командам CI удалять локальную/боевую БД.
4. Настрой cache для pnpm по lockfile; это оптимизация, а не замена проверок.
5. Скрипты в корне должны иметь ясные названия и корректные exit codes: не использовать `|| true`, `echo success` вместо тестов, заглушки, скрывающие пропуск.
6. Добавь минимум один unit-тест доменной утилиты/контракта, одну DB integration проверку и один build smoke; убедись, что тесты не зависят от порядка запуска.
7. Добавь локальный `pnpm verify` (или документированную эквивалентную цепочку), который повторяет логику CI.

## Acceptance criteria

- [x] Все проверки реально проходят локально на Windows и в чистой Linux-копии; GitHub hosted run отдельно отмечен NOT RUN.
- [x] Workflow содержит DB service и реальные интеграционные тесты, а не только lint.
- [x] `pnpm install --frozen-lockfile` без интерактивных prompts.
- [x] Нет secrets в workflow и в логах.
- [x] Build Web и worker не требует продакшн Telegram/AI ключей.

## Проверки

Локально `pnpm verify`, `pnpm build`, `pnpm test:integration`; `git diff --check`. Если возможен запуск Actions — указать URL/run status только при реальном успешном выполнении.

## Вне scope

CD/deploy production, SaaS-платежи, E2E языкового сценария, AI-evals (позднее).

## Реализация и проверки · 2026-11-12

Workflow: `.github/workflows/ci.yml`; общая локальная/CI цепочка:
`scripts/verify.ts`. Подробные команды, service/env/cache и ограничения:
[docs/CI.md](../CI.md).

CI использует Node 24.22.2 из .nvmrc, pnpm 10.34.9 из packageManager и
исходный PostgreSQL 18.6 image digest. Actions закреплены полными SHA.
У каждого job отдельный service с lifeos_test_ci; production DATABASE_URL и
repository secrets не используются. Cache касается только pnpm store по
lockfile, а verify принудительно выполняет Turbo tasks.

Добавлены root tooling lint/typecheck и реальные проверки пустого domain
без фиктивных build/test scripts. Новые тесты: contract boundary для UUID,
две негативные проверки test migration CLI, PostgreSQL-проверка двух запусков
этого CLI и build smoke production Web/compiled worker. Существующие
contract/DB/worker suites включены в verify без пропусков.

Windows использует существующий portable Node 24.22.2 / pnpm 10.34.9.
Linux rehearsal выполнен в одноразовом Node 24.22.2 bookworm-slim контейнере
с digest `sha256:01d566e8d94d8c619591d78652babfccd3c6992a3dffa9ed5ab39e11cf6c70e9`:
исходники скопированы без .git/node_modules/.env/cache, dependencies установлены
заново, PostgreSQL — отдельный локальный test instance. Это Debian Linux
rehearsal, а не GitHub-hosted Ubuntu run и не проверка WSL2.

GitHub remote и доступ к metadata подтверждены. **GitHub Actions run: NOT RUN** —
новый workflow и код предыдущих этапов пока находятся в незакоммиченном рабочем
дереве; запуск именно этого состояния требует его публикации. URL успешного
run не заявляется. После review нужен обычный commit/push или pull request.
Production deployment и LFS-109 автоматически не выполнялись.
