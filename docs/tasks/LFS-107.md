# LFS-107 — Доказать атомарность и идемпотентность «DB write + job»

**Зависимости:** LFS-105, LFS-106  
**Цель:** практическим интеграционным тестом проверить ключевое архитектурное обещание pg-boss: job и доменная запись фиксируются в одной PostgreSQL транзакции.

## Задание Codex

1. На базе `packages/db` создай **временную test-fixture таблицу** `foundation_test_operations` (или схожее имя) с `id`, `idempotency_key UNIQUE`, `created_at`, `payload`; не создавать `activity_events` (это LFS-210).
2. Реализуй в отдельном тестовом/внутреннем модуле атомарную функцию: открыть Drizzle transaction → вставить fixture запись → поставить pg-boss demo job **используя именно transaction-bound adapter** → commit. По закреплённой версии pg-boss проверь официальный `fromDrizzle(tx, sql)` или поддерживаемую альтернативу: не выдумывать API.
3. Напиши интеграционные тесты **на настоящем PostgreSQL**:
   - **commit:** запись и job появляются совместно;
   - **rollback:** принудительная ошибка после постановки job → ни запись, ни job не остаются;
   - **dedupe:** одинаковый `idempotency_key` не создаёт 2 бизнес-операции;
   - **concurrent dedupe:** два конкурентных запроса с одинаковым ключом приводят к одному итоговому действию (если это реализуемо в выбранном тестовом стенде).
4. Проверяй эффект через SQL/статус job; не опирайся на случайный timing или на заготовленный mock.
5. Подробно опиши в `docs/adr/002-queue-atomicity.md`, почему выбранная интеграция атомарна, какие ограничения pg-boss остаются (`at least once` при worker processing), чем обеспечена идемпотентность в producer/consumer.
6. **Если драйвер/версии не поддерживают transaction-bound enqueue:** не маскируй проблему. Сначала исследуй совместимую альтернативу или transactional outbox, документируй выбор и не отмечай критерии атомарности выполненными без теста.

## Acceptance criteria

- [x] Все 3 обязательных теста (commit, rollback, sequential dedupe) реально проходят на PostgreSQL; concurrent dedupe также проходит.
- [x] Rollback удаляет и fixture write, и поставленную job из видимости очереди.
- [x] Нет нового Redis или другой очереди.
- [x] Есть ADR с проверенным кодом/способом transaction adapter.
- [x] Нет production таблиц `users`, `goals`, `activity_events`.

## Реализация и проверки · 2026-11-12

Test-only код: `packages/db/tests/fixtures/atomic-operations.ts`, DDL:
`packages/db/tests/fixtures/atomicity.sql`, suite:
`packages/db/tests/integration/atomicity.test.ts`.
Подробное решение: [ADR queue atomicity](../adr/002-queue-atomicity.md).

Проверен официальный `fromDrizzle(tx, sql)` из установленного pg-boss 12.38.1
с Drizzle 0.45.4 и pg 8.23.1. При enqueue adapter использует текущую Drizzle
transaction. Commit-тест сравнивает backend PID/transaction ID и видимость
через независимый pool до/после commit. Rollback вызывается после реального
enqueue; ни операция, ни job не остаются, тот же ключ можно использовать снова.

UNIQUE idempotency_key и READ COMMITTED согласуют последовательные и
конкурентные запросы. Concurrency-тест через barrier открывает две реальные
транзакции на разных PID до INSERT. Разные действия с тем же ключом отклоняются;
новые trace IDs при retry не создают новую job. Дополнительно проверены
невалидный ввод, ошибка enqueue и реальный `null` при конфликте job ID.

Test-only consumer хранит SQL-эффект и processed marker в одной транзакции
под row lock. Проверены rollback эффекта, replay до acknowledgment и
конкурентная повторная обработка. Production worker не изменён; внешние
эффекты и идемпотентность будущих бизнес-handlers этим не покрываются.

Окружение: Windows x64, portable Node.js 24.22.2, pnpm 10.34.9,
PostgreSQL **18.6 (Debian 18.6-1.pgdg12+2)** на отдельном test instance.
URL и пароли не выводились. Версии зависимостей не обновлялись.
