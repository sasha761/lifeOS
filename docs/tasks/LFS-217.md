# LFS-217 — Правка старта и цели до первого измерения

**Этап:** 2 — LifeOS Core (вставка в очередь после LFS-216, перед Stage 3, по запросу владельца 2026-11-18)
**Зависимости:** LFS-205, LFS-206, LFS-207, LFS-213; [ADR-007](../adr/007-goals.md), [ADR-009](../adr/009-goal-measurements.md)
**Цель:** пока у цели нет измерений, пользователь может изменить её единицу, старт, цель и направление; срок
везде явно необязателен.

## Почему

ADR-007 запрещает менять определение цели после создания, чтобы правка не переосмыслила уже введённые
измерения. Пока измерений нет, переосмыслять нечего, а ошибка в старте или единице сейчас исправляется только
архивом и новой целью. Пример целей (LFS-218), который пользователь загружает по своему выбору, содержит
примерные стартовые значения, которые нужно суметь поправить под себя.

Срок в контракте и форме уже необязателен (`due_at` по умолчанию `null`, поле без `required`), но по форме
этого не видно. Владелец не хочет, чтобы срок воспринимался как обязательный.

## Решения владельца · 2026-11-18
1. Единица (и своя единица), старт, цель и направление меняются, **пока у цели нет измерений**. После первого
   измерения — как сейчас, только название, описание и срок.
2. Срок помечается как необязательный; пустое поле — цель без срока.

## Область изменений
- `packages/contracts/src/goals.ts` — расширение `updateGoalInputSchema`; `activity-events.ts`, `activity.ts` —
  новые значения `changed_fields`
- `packages/domain`, `packages/db` — команда правки с проверкой отсутствия измерений под блокировкой строки цели
- `apps/web/components/goals/goal-form.tsx`, `lib/goal-form-input.ts`, `lib/activity-presentation.ts`
- ADR-007 (дополнение), `docs/api/contracts.md`

## Задание
- [x] PATCH цели принимает `unit`, `unit_label`, `baseline`, `target`, `direction` вместе с прежними полями;
  итоговое определение проверяется целиком теми же правилами, что при создании (направление, точность единицы,
  своя единица).
- [x] Если у цели есть хотя бы одно измерение — 409 `CONFLICT` с понятной безопасной ошибкой, ничего не меняется.
  Гонка «добавление измерения ↔ смена единицы» не даёт измерения в старой единице у цели с новой
  (блокировка строки цели или проверка в той же транзакции; составной FK по `unit` уже защищает от несовпадения).
- [x] Архивная цель не меняется (как сейчас).
- [x] Аудит: `goal.updated` с before/after новых полей; журнал показывает «Старт изменён: 2 → 3»,
  «Единица изменена» и т. п.
- [x] UI «Изменить цель»: при отсутствии измерений — поля Единица / Старт / Цель (и направление), как в диалоге
  создания; после первого измерения — короткая подсказка «Старт и цель фиксируются после первого измерения».
- [x] Поле «Срок» в создании и правке подписано «Срок · необязательно»; в правке есть способ убрать срок.

## Acceptance criteria
- [x] Тесты контракта: допустимые и недопустимые сочетания; integration: правка без измерений с аудитом, 409 при
  наличии измерения, гонка, чужой пользователь, архив.
- [x] e2e: правка старта новой цели, затем измерение, после которого поля старта недоступны; цель без срока.
- [x] `pnpm verify`, `pnpm test:ui` зелёные.

## Вне scope
Перенос цели в другую сферу, пересчёт или конвертация существующих измерений, правка после первого измерения.

## Результат LFS-217 · 2026-11-19

Ветка `lfs-217-goal-definition-edit` (от `8d5a9a6`, LFS-216). Миграций нет. Владелец доверил выбор решений
исполнителю («как лучше для проекта»); принятые решения записаны в дополнении LFS-217 к
[ADR-007](../adr/007-goals.md#дополнение-lfs-217--2026-11-19).

### Что сделано

- **Контракт** (`packages/contracts/src/goals.ts`): `updateGoalInputSchema` принимает определение целиком —
  `unit`, `unit_label`, `baseline`, `target`, `direction` вместе — и проверяет его правилами создания; частичное
  определение — 400. `GOAL_DEFINITION_FIELDS`, `GOAL_METADATA_FIELDS`.
- **Домен** (`packages/domain/src/core/goals.ts`): изменённые поля считаются по всем восьми полям; новое
  определение у цели с измерениями — `CONFLICT`; то же определение без изменений отбрасывается, поэтому metadata
  цели с измерениями сохраняется как раньше. Проверка идёт под `FOR UPDATE` строки цели — той же блокировкой,
  которую первой берут записи измерений.
- **DB** (`packages/db/src/repositories/goals.ts`): `hasMeasurements`; UPDATE пишет определение только группой
  и с условием `NOT EXISTS (goal_measurements)`; составной FK по `unit` остаётся третьим барьером.
- **Аудит и журнал**:
  - `changed_fields` у `goal.updated` — до 8 значений (`GOAL_CHANGED_FIELDS`); значения определения уже были в
    before/after snapshot, SQL CHECK списка не ограничивает — миграция не нужна;
  - запись журнала получила `definition { before, after }`; тексты «Старт изменён: 2 → 3», «Цель изменена: …»,
    «Единица изменена: NOK → шт.», «Направление изменено: увеличить → уменьшить», «Название единицы изменено»;
  - история не переосмысляется: журнал не хранит единицу измерения, поэтому измерения, записанные до последней
    смены единицы или своей единицы, показываются числом без единицы (`measurement.unit = null` в журнале и в
    Dashboard). Время смены — коррелированный подзапрос на каждую строку в `activity-reader` и
    `dashboard-reader`: индекс `(user_id, goal_id, occurred_at, id)` сужает поиск до событий цели, тип события и
    `changed_fields` проверяются построчно.
- **UI**:
  - «Изменить цель» у цели без измерений показывает направление и ряд Единица / Старт / Цель / Срок, свою единицу
    и предпросмотр формулы, как диалог «Новая цель»; после первого измерения — только название, описание, срок
    и подсказка «Старт и цель фиксируются после первого измерения…»;
  - поле срока подписано «Срок · необязательно» в создании и правке; кнопка «Убрать срок» очищает дату и
    возвращает фокус в поле;
  - текст 409 упоминает появившиеся измерения.
- **Тесты**:
  - contracts: полное и частичное определение, недопустимые сочетания, новые `changed_fields`, `definition` и
    `unit: null` в записи журнала;
  - domain: правка без измерений с аудитом, 409 с измерением, сохранение metadata при том же определении,
    правила создания; журнал — значения определения и единица у старых измерений;
  - PostgreSQL integration `goal-definition.test.ts` (5): HTTP-правка и пересчёт прогресса, 409 и неизменность,
    чужой пользователь, архив, SQL guard без проверки сервиса, гонка PATCH ↔ первое измерение (8 раундов,
    единица измерения всегда совпадает с единицей цели), журнал и Dashboard после смены единицы;
  - web unit: форма (определение уходит только когда показано), подписи, тексты журнала;
  - Playwright `goal-definition.spec.ts`: правка старта, цели и срока, снятие сохранённого срока «Убрать срок»
    (в журнале «срок изменён: … → без срока»), измерение 20%, после которого
    поля определения скрыты.
- **Документы**: ADR-007 (дополнение), ADR-010, `docs/api/contracts.md`; снимки `goal-edit` и
  `goal-edit-measured` в `pnpm ui:shots`.

### Ограничения

- Клиент API, который хочет поменять только цель, присылает определение целиком; сейчас такой клиент один — UI.
- Измерения, записанные до смены единицы, в журнале теряют единицу и показываются числом: прежняя единица
  в журнале не хранится, и выдумывать её нельзя.
- Примерные измерения из LFS-218 пока не существуют; правило «не мешают правке» добавит LFS-218.
- Подзапрос времени смены единицы выполняется на каждую строку журнала и Dashboard и перебирает события цели:
  стоимость — строки × события цели. На текущих объёмах это незаметно; при росте журнала считать время один раз на
  цель (кандидат — [LFS-214](LFS-214.md)).
- Время событий хранится с точностью до миллисекунды. Измерение, записанное в ту же миллисекунду, что и смена
  единицы, журнал покажет числом без единицы: это безопаснее, чем показать его в чужой единице.
- Откат кода к LFS-216 после правки определения несовместим с журналом — см. раздел «Миграция и откат»
  [ADR-007](../adr/007-goals.md#миграция-и-откат).
