# LFS-216 — Удаление целей

**Этап:** 2 — LifeOS Core (вставка в очередь **после LFS-213, перед Stage 3**, по запросу владельца 2026-11-18)
**Зависимости:** LFS-207, LFS-210, LFS-213; [ADR-007](../adr/007-goals.md), [ADR-008](../adr/008-transactional-audit.md),
[ADR-010](../adr/010-goals-api-progress.md)
**Цель:** пользователь может навсегда удалить свою цель, активную или архивную, вместе с её измерениями и историей.

## Почему

Сейчас цель можно только перенести в архив, и это окончательно: ADR-007 и ADR-010 прямо исключают hard delete,
`DELETE /api/v1/goals/:id` отвечает 405. При этом Master Plan для этапа 2 перечисляет `GET/PATCH/DELETE /api/v1/goals/{id}`.
Ненужная или созданная по ошибке цель (а после LFS-218 — неподходящая стартовая) навсегда остаётся в «Архиве».

## Решения владельца · 2026-11-18
1. **Удаление навсегда, с подтверждением.** Цель, её измерения, записи журнала и квитанции команд удаляются
   в одной транзакции. Корзины и восстановления нет. В БД это уже обеспечено `ON DELETE CASCADE` (ADR-008).
2. Удалять можно и активные, и архивные цели.
3. «Проекты» отдельной сущностью пока не существуют: Projects — одна из шести сфер, её цели удаляются так же,
   как любые другие. Сами сферы — фиксированный реестр (LFS-203), их удаление вне scope.

## Область изменений
- `packages/contracts` — DTO ответа удаления, при необходимости — новая операция квитанции
- `packages/domain` — команда `deleteGoal` в сервисе целей (owner-scoped, без SQL в обход репозиториев)
- `packages/db` — unit of work удаления; миграция, только если её требует идемпотентность (согласовать в плане)
- `apps/web/server/goals.ts`, `app/api/v1/goals/[goalId]/route.ts` — `DELETE`
- `apps/web/components/goals/goal-detail.tsx` — команда «Удалить цель» в меню «⋯» и диалог подтверждения
- ADR-007 и ADR-010 — раздел о hard delete; `docs/api/contracts.md`

## Задание
- [x] `DELETE /api/v1/goals/:id`: только владелец; чужой и несуществующий id неотличимы (404); гость — 401;
  тело запроса отклоняется, как у `DELETE` измерения; те же Origin/CSRF-проверки, что у остальных записей.
- [x] Идемпотентность: повтор с тем же `Idempotency-Key` после обрыва связи не показывает пользователю ошибку.
  Квитанции сейчас каскадно удаляются вместе с целью, поэтому способ (квитанция без FK на цель или «уже удалено»
  как успешный исход) выбрать в плане.
- [x] Транзакция: при ошибке не удаляется ничего; параллельное добавление измерения не оставляет «сирот».
- [x] UI: «Удалить цель» в меню «⋯» для активной и архивной цели. Диалог `alertdialog` «Удалить цель?
  Измерения и история тоже удалятся. Это нельзя отменить.» с кнопками «Удалить» (опасный тон) и «Отмена»;
  Escape и «Отмена» возвращают фокус на «⋯». После удаления — `/goals` с прежними фильтрами, сообщение «Цель удалена»,
  счётчики во вкладках и Dashboard обновлены.
- [x] ADR-007 и ADR-010: hard delete теперь есть; архив не меняется — окончательный, данные сохраняются.

## Acceptance criteria
- [x] PostgreSQL integration: удаление стирает цель, измерения, события и квитанции; второй пользователь не может
  удалить чужую цель и не теряет своих данных; повтор запроса; откат при сбое.
- [x] HTTP-тесты: 401, 404, тело запроса, Origin.
- [x] e2e на 1280 и 390: удаление из меню с подтверждением, отмена по Escape, фокус, обновлённые счётчики.
- [x] `pnpm verify`, `pnpm test:ui` зелёные.

## Результат LFS-216 · 2026-11-18

### Реализовано

`GoalsService.deleteGoal` удаляет активную или архивную цель через owner-scoped
repository в READ COMMITTED транзакции. FOR UPDATE родителя сохраняет порядок
блокировок измерений. FK CASCADE удаляет измерения, события и прежние квитанции;
нового события об удалении нет. Ошибка вставки квитанции удаления откатывает
всю операцию, включая каскады.

Выбранный перед реализацией способ идемпотентности — отдельная минимальная
`goal_deletion_receipts` без FK на цель: owner/key, fingerprint, UUID цели,
время. Миграция `0006_goal_deletion_receipts` добавляет только эту таблицу.
Это позволяет одновременно отвечать 404 на чужой/неизвестный id и 200 на
повтор уже принятого удаления с тем же ключом. Общий advisory lock и проверки
обеих таблиц сохраняют namespace ключей всех goal/measurement команд.
Текст цели, измерения, журнал и прежние квитанции после удаления не сохраняются.

HTTP DELETE использует прежний envelope/no-store и session guard перед любым
чтением входных данных. Тело, query и неверный Idempotency-Key отклоняются.
Общая проверка Origin всех записей сравнивает его с публичным BETTER_AUTH_URL,
а не внутренним request.url Next или входящими Host headers. 403 — определённый
отказ без записи: клиент разрешает отменить действие, не блокируя форму для повтора.

«Удалить цель» доступно в «⋯» активной и архивной цели. Нативный `alertdialog`
с предупреждением, опасным тоном удаления, фокусом на «Отмена» и trap Tab
использует существующий Modal. Escape/отмена возвращают фокус на «⋯».
После успеха удалённая панель закрывается, список и Dashboard counters читаются
заново, `/goals` сохраняет фильтры и сообщает «Цель удалена». При обрыве связи
повторяет прежний ключ; отмена недоступна только до определённого результата.

### Ручные действия и риски

- Перед запуском новой версии применить `pnpm db:migrate` к основной локальной
  БД. В этой задаче миграции и удаление проверяются на dedicated test DB и
  изолированных схемах; основная БД не изменяется.
- Данные цели после подтверждения восстановить нельзя. Минимальная квитанция
  удаления хранится до удаления владельца; истечение ключей вне scope Stage 2.
