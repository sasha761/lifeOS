# Интерфейс LifeOS: как делать строго по макетам

Правило для Codex и Claude Code. Действует в каждой задаче, которая меняет интерфейс.
Решение о дизайне — [ADR-011](adr/011-design-system-v2.md), список страниц и макетов — [PAGES.md](reference/ui/PAGES.md).

## 1. Источники правды, по порядку

1. **Токены** в `apps/web/app/globals.css`. Это единственное место, где живут цвета, радиусы и шрифт.
2. **Общие компоненты** `apps/web/components/ui/*` и классы из `globals.css` (`action-link`, `action-link-secondary`,
   заголовок страницы). Если подходящий компонент есть, используется он, своя копия не делается.

   | Элемент макета | Компонент или класс (LFS-212) |
   |---|---|
   | заголовок страницы, подзаголовок с жирным началом, действия справа | `PageHeader` |
   | карточка `.card` с заголовком и действием справа; пунктирная «появится позже» | `SectionCard` (`variant="dashed"`), основа — `Card` |
   | плитка «подпись · число · пояснение» (Рекорды; в панели цели плиток нет с LFS-224) | `StatCard` |
   | «◉ ручной ввод · 12.11» | `SourceLabel` |
   | полоса прогресса `.bar` цветом сферы | `ProgressBar` (нативный `<progress>`) |
   | квадрат сферы `.dom` с заливкой | `DomainIcon` (`sm` 22 / `md` 30 / `lg` 44 px) |
   | чип `.chip`, `.c-g`…, `.c-x` | `StatusChip` (`tone`: цвет сферы/статуса, `neutral`, `outline`) |
   | переключатель вида `.seg` (ссылки) | `SegmentedTabs` (`size="sm"` — размер макета) |
   | выбор одного из вариантов в форме (`.seg` в диалоге) | `SegmentedChoice` (нативные radio) |
   | кнопки `.btn` / `.btn.s` | `action-link` / `action-link-secondary` + `action-compact` / `action-sm` |
   | подпись поля `.lbl` | `field-label`; поле — `field-control` |

   Цвет сферы задаётся один раз: `tone` в `apps/web/lib/domain-presentation.ts`.
3. **Макет страницы** в `docs/reference/ui`:
   - `NN-name.png` показывает, как экран должен выглядеть;
   - `html/NN-name.html` даёт точные размеры, отступы и цвета: откройте в браузере или читайте CSS прямо в файле.
4. **Данные** только из реальных записей. Числа, слова и компании на макетах примерные.

Если спека §16 и макет расходятся в мелочах (размер шрифта, отступ), прав макет. Крупное расхождение — вопрос владельцу.

## 3. Запрещено

- Цвета в `hex`, `rgb()` или `oklch()` в компонентах и `className`. Цвет есть только в `globals.css`.
  `pnpm lint` проверяет это правилом `lifeos-ui/no-color-literals` для `apps/web/app` и `apps/web/components`
  (`#rgb`, `#rrggbb`, `rgb(`, `hsl(`, `oklch(`, `color-mix(` и т. п., в том числе внутри `bg-[…]`, `shadow-[…]`).
  Тени тоже токены: `shadow-popover`, `shadow-dialog`.
- Новый цвет, радиус или шрифт без ADR.
- Своя кнопка, чип, карточка или переключатель, если в `components/ui` уже есть такой.
- Переносить в код данные с макета или показывать процент без данных.
- Показывать кнопки разделов, которых ещё нет.

## 4. Допустимые отличия от макета

- Реальные данные, тексты и число строк.
- Перенос строки или сдвиг блоков вниз из-за текста или кнопки, которых нет на макете. Такое отличие всё равно
  вносится в таблицу отличий с причиной. При этом **должны совпадать с макетом**: порядок элементов, ряды
  и выравнивание, цвета, шрифты и другие токены. Отличие в них исправляется, а не только описывается в отчёте
  (решение владельца 2026-11-20).
- Блоки модулей, которых ещё нет: их не показываем.
- Размеры в пределах ±2px из-за сетки Tailwind.
- Доступность важнее макета: если контраст или фокус по макету хуже нормы, делаем по норме и пишем об этом в отчёте.
- Мобильная версия по правилам раздела 6.

## 5. Обязательная визуальная проверка

В каждой задаче, которая меняет интерфейс:

1. **До кода** открыть PNG и HTML макета и выписать элементы экрана сверху вниз: блоки, заголовки, кнопки,
   переключатели, чипы, подписи источников.
2. **После кода** снять скриншоты страницы на 1440×900 и 390×844: `pnpm db:test:up`, затем `pnpm ui:shots`
   (Playwright, тестовый пользователь из e2e, изолированная схема тестовой БД). Результат в `.cache/ui-shots/`:
   `<страница>-1440.png`, `-390.png` и `<страница>-compare.png` (слева макет, справа реализация), `report.json`
   (горизонтальная прокрутка, ошибки страницы, внешние запросы). Новую страницу добавьте в список `shots`
   в `apps/web/scripts/ui-shots.ts`.
3. **Сравнить** скриншот с макетом по списку из шага 1. Каждое отличие исправить или объяснить по разделу 4.
4. **В отчёт** добавить таблицу «элемент макета → совпадает / отличается / нет, причина» и пути к скриншотам.
5. **Ревьюер** (второй агент) повторяет сравнение по тем же скриншотам. Необъяснённое отличие — блокер.

## 6. Мобильная версия (390px)

Макеты нарисованы для 1440px, кроме Mini App. На узком экране:

- верхняя полоса компактная, разделы в меню-шторке;
- правая панель уходит под основной контент;
- сетки 4 → 2 → 1 колонка;
- таблицы превращаются в список карточек;
- боковые отступы 16px, без горизонтальной прокрутки.

## 7. Добавка к промпту любой UI-задачи

```text
Интерфейс делай строго по docs/UI_GUIDELINES.md и макету docs/reference/ui/NN-name.png
(точные размеры и отступы — docs/reference/ui/html/NN-name.html; какой макет к какой странице — PAGES.md).
Цвета и радиусы только токенами из globals.css, без hex в компонентах; переиспользуй components/ui.
До кода выпиши элементы макета. После кода сними скриншоты 1440 и 390 (pnpm ui:shots → .cache/ui-shots), сравни с макетом
и дай в отчёте таблицу отличий с причинами. Данные с макета в код не переносить.
```
