Задача и уточнения владельца: $ARGUMENTS

Первое слово — LFS-ID (дальше «ID»). Выполняешь только его.

Если ID не указан (аргументов нет или первое слово не похоже на `LFS-<число>`), найди следующую задачу сам:

1. Прочитай `docs/tasks/README.md`: таблицы очереди (колонка «Очередь», если есть) и строки статуса под ними. Если там прямо написано «Следующая задача по очереди — …», это и есть кандидат.
2. Если такой строки нет, возьми первую задачу по порядку очереди без отметки о выполнении (раздел «Результат …» в её `docs/tasks/<ID>.md` или запись в строках статуса).
3. Проверь, нет ли в `docs/tasks/` задачи, вставленной в очередь перед кандидатом (в шапке пометка вроде «вставка в очередь перед LFS-XXX») и ещё не выполненной. Если есть, кандидат — она.
4. Покажи владельцу ID, короткое название, цель задачи из её шапки, зависимости и их статус, а также откуда ты это взял. Если кандидатов несколько или очередь неоднозначна, перечисли их.
5. Спроси подтверждение и остановись. Ничего не читай сверх этого и не начинай подготовку, пока владелец не ответит. Уточнения владельца из аргументов (если они были без ID) примени к подтверждённой задаче.

## 1. Подготовка (только чтение)

1. Прочитай `docs/DEVELOPMENT_WORKFLOW.md`, `docs/tasks/README.md` и `docs/tasks/<ID>.md`.
2. Прочитай все ADR, task-файлы и документы, на которые ссылается задача. Картинки-референсы открой инструментом Read.
3. Если есть `docs/tasks/<ID>-*PROMPT*.md`, выполни его указания. Они написаны для Codex и относятся к тебе так же.
4. Проверь `git status --short`, `git branch --show-current`, `git log --oneline -5`.

Остановись и спроси владельца, если:
- задачи `<ID>` нет, или она не следующая по очереди в `docs/tasks/README.md`, или её зависимости не выполнены;
- в рабочем дереве есть незакоммиченные изменения, которые пересекаются с файлами этой задачи. Предложи сначала закоммитить их отдельно.

## 2. План

Покажи план: какие файлы изменятся, порядок шагов, какие проверки запустишь, риски и вопросы.
Файлы не меняй, пока владелец не ответит «ОК».

## 3. Реализация

- Ровно один ID. Ничего из следующих задач и этапов.
- Порядок из AGENTS.md: контракты и типы, затем реализация, затем тесты, затем документация.
- Новые зависимости ставь только с точной версией в `pnpm-lock.yaml`. Метод SDK сверяй с официальной документацией установленной версии.
- Для `apps/web` сначала читай нужный раздел `apps/web/node_modules/next/dist/docs/`.
- Никаких демо-данных с макетов и фиктивных метрик.

## 4. Проверки

Запусти реальные команды из acceptance criteria задачи (обычно `pnpm db:test:up`, затем `pnpm verify`; для UI ещё `pnpm test:ui`).
Каждую отметь как PASS, FAIL или NOT RUN с точной причиной. Не выдавай непройденное за пройденное и не перезапускай без нужды то, что уже прошло.

## 5. Отчёт

- Допиши в `docs/tasks/<ID>.md` раздел «Результат <ID> — <дата>» и строку статуса в `docs/tasks/README.md`, как это сделано у предыдущих задач.
- Ответь владельцу в формате «Структура результата» из AGENTS.md и добавь `git diff --stat` и `git status --short`.
- Не коммить, не пушь и не начинай следующий ID без разрешения владельца.
